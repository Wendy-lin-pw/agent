# 计算机类课程教学智能体 —— 项目设计方案

## 一、功能介绍

**选定功能点：课程文档知识点整理与标签检索。**

- **教师端**：上传课程文档（Markdown / TXT，框架阶段支持纯文本，PDF 解析为后续迭代）；
- **智能体介入**：系统调用大模型，自动完成两件事：
  1. 从文档中抽取结构化知识点（标题 + 内容摘要）；
  2. 为每个知识点打 3~5 个标签（如「二叉树」「时间复杂度」「动态规划」）；
- **学生端**：按标签检索知识点，例如点选「动态规划」即可看到所有相关知识点及其来源文档。

该功能解决的真实痛点：课程文档（课件、讲义）内容分散，学生检索困难；人工整理知识点耗时。让大模型承担"整理 + 打标"这种非精确但格式化的工作，教师只做审核，学生获得统一入口。

## 二、大模型介入方式的合理性分析

**介入方式：云端 LLM API（OpenAI 兼容接口），Prompt 约束输出 JSON，无本地模型。**

| 备选方案 | 结论 |
|---|---|
| 本地部署开源大模型（如 Qwen/DeepSeek 本地推理） | ❌ 需要 GPU 服务器，成本数万元级；本任务无需模型微调，不划算 |
| 云端 LLM API（**采用**） | ✅ 按量付费、零 GPU、随时换模型；知识点抽取属于**非实时、可异步**的任务，对 API 延迟不敏感 |
| 传统 NLP（TF-IDF / TextRank 抽关键词） | 只能抽词不能生成摘要和语义标签，效果上限低；可作为兜底降级方案 |

合理性论证：

1. **任务匹配**：抽取知识点 + 打标签是典型的"理解 + 生成"任务，正是 LLM 强项；而它不要求 100% 精确（教师可审核修改），允许 LLM 的概率性。
2. **架构合理**：LLM 只在"文档上传后"被调用一次，不参与学生检索链路——学生搜索走纯数据库查询，响应快且不产生 token 费用。
3. **工程可控**：通过 Prompt 严格约束 JSON 输出 + 程序解析校验，失败则重试/标记失败，不会污染数据库。
4. **可演进**：后续若要做"语义搜索"，只需在抽取阶段追加向量 embedding 存入向量库（RAG），架构上预留了 `services.py` 扩展点，不影响现有链路。

## 三、数据来源、数据库设计与可行性

### 3.1 数据来源

- **课程文档**：教师上传的 Markdown / TXT 讲义（框架阶段），PDF/DOCX 解析后续接入；
- **知识点与标签**：由大模型从文档中生成，落入数据库后教师可在后台审核修正（标签也可人工增删）。

### 3.2 数据库设计（MySQL，3 张核心表）

```
Document（课程文档）           KnowledgePoint（知识点）        Tag（标签）
├─ id                        ├─ id                          ├─ id
├─ title                     ├─ document_id → Document      ├─ name (UNIQUE)
├─ file                      ├─ title                       └─ created_at
├─ status(待处理/抽取中/      ├─ content
│   已完成/失败)              └─ created_at
├─ error_message
└─ uploaded_at
                              KnowledgePoint ←M2M→ Tag（知识点标签关联表）
```

设计要点：

- 知识点与标签为多对多，一个标签挂多个知识点，一次检索命中全部；
- `Tag.name` 唯一约束，避免「动态规划/DP」这类同义标签泛滥，同义合并是后续运营问题；
- `Document.status` 状态机记录抽取流水线状态，失败原因落库，便于运维排查；
- 检索走 `tags__name` 索引查询，数据量在万级以下时 MySQL 足够，无需引入搜索引擎。

### 3.3 可行性

- **技术可行**：Django + MySQL + 云 LLM API 全是成熟技术栈；核心代码量小（本仓库框架已可运行）；
- **经济可行**：无 GPU、无本地模型，唯一变动成本是 API 调用费。按一学期 200 份文档、每份 6K tokens 估算，调用费约几十元；
- **运营可行**：教师上传 → 系统抽取 → 教师审核 → 学生检索，流程与现有教学习惯一致，无需改变授课方式。

## 四、部署方案与后期运维

### 4.1 部署方案（对应 K8s Master / Worker 架构）

```
                    ┌─────────────────────────────┐
   学生/教师 ──HTTP──▶  K8s Ingress                  │
                    │   └─ Web Pod (Django+gunicorn)│
                    │        │ 投递抽取任务           │
                    │   ┌────▼─────┐    ┌─────────┐ │
                    │   │ 队列/任务  │◀──│ Worker  │ │──▶ 云 LLM API
                    │   │ (Celery) │    │ Pod ×N  │ │    (外网 HTTPS)
                    │   └──────────┘    └─────────┘ │
                    │   MySQL (StatefulSet / 云RDS)  │
                    └─────────────────────────────┘
```

- **Master 节点**：运行控制面；**Web Pod** 承载 Django（gunicorn），**Worker Pod** 消费抽取任务、调用云 LLM API 后写库；
- Web 与 Worker 分离是关键设计：LLM 调用耗时长（10s+），不能阻塞学生检索请求；
- Worker 无状态、可水平扩缩容——上传高峰（开学前两周）扩到 4 副本，平时 1 副本；
- MySQL 建议直接用云数据库 RDS（自动备份、主从），课程数据量小，最低规格即可；
- 小规模（一个学院以内）可先用 docker-compose 单机部署，K8s 是规模化后的演进，两者镜像相同。

### 4.2 后期运维说明

| 事项 | 措施 |
|---|---|
| 监控 | K8s + Prometheus 监控 Pod 状态、任务队列积压；Document.status=failed 比例告警 |
| 日志 | Worker 记录每次 LLM 调用的耗时与 token 消耗，落 ELK / 云日志服务 |
| 备份 | MySQL 每日自动备份（云 RDS 自带）；媒体文件（上传文档）每日快照 |
| LLM 降级 | API 超时/失败自动重试 2 次后标记 failed；密钥故障时可切换备用服务商（OpenAI 兼容接口可平替） |
| 内容审核 | 大模型输出先入"待审核"状态，教师确认后对学生可见，防止幻觉知识点误传 |
| 安全 | API Key 只存 K8s Secret / 环境变量；文档上传限制类型与大小（≤10MB） |

## 五、甲方部署费用（硬件要求）

**方案 A：单机 docker-compose（≤500 用户，推荐起步）**

| 项目 | 规格 | 年费用（参考） |
|---|---|---|
| 云服务器 ECS | 2 核 4G，系统盘 50G | 约 ¥1,000~1,500/年 |
| 云数据库 RDS MySQL | 最低规格（1 核 2G） | 约 ¥1,000/年（或先用 ECS 自装 MySQL，¥0） |
| 域名 + SSL | 1 个 | 约 ¥100/年 |
| **合计** | | **约 ¥2,000~2,500/年** |

**方案 B：K8s 集群（多校区 / >2000 并发用户时演进）**

| 项目 | 规格 | 年费用（参考） |
|---|---|---|
| K8s Master | 2 核 4G ×1 | 约 ¥1,500/年 |
| Worker 节点 | 4 核 8G ×2（可弹性） | 约 ¥5,000/年 |
| 云 RDS MySQL 高可用版 | 2 核 4G | 约 ¥3,000/年 |
| **合计** | | **约 ¥10,000/年** |

**重要说明：两种方案均无 GPU 需求**——大模型走云 API，这是本方案硬件成本可控的核心原因。变动成本仅 LLM API 调用费，按上文估算每学期约几十至一两百元，可忽略。

## 附：仓库运行方式

```bash
make venv && make install && make migrate && make run
# 上传: curl -F file=@讲义.md http://127.0.0.1:8000/api/documents/
# 抽取: curl -X POST http://127.0.0.1:8000/api/documents/1/extract/
# 检索: curl "http://127.0.0.1:8000/api/knowledge/?tag=示例标签"
```
